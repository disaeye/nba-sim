# NBA-Sim · 愿景与目标宪章

> 定位：全文档体系的目标锚。本文档回答“要做出什么、什么算好、哪些红线不可放宽”。系统组织见 `docs/architecture.md`，质量观测见 `docs/quality.md`，过程验收见 `docs/protocol.md`。
> 修订纪律：本文档只定义稳定目标和约束，不记录当前实现、周期结果、执行命令或历史快照。

## 1. 这个引擎是什么

NBA-Sim 是一个**过程优先的篮球比赛模拟引擎**：给定球员档案、球队组织、联赛规则和随机种子，从跳球到终场逐步生成比赛过程。

核心产物是：

- 可重放的事实事件流；
- 可观察的逐步状态投影；
- 能从事实独立重建的比分、时钟、球权、犯规和回合摘要；
- 能定位到回合、事件和责任子系统的评判工件。

观察者、回放、统计和 UI 只能消费引擎发布的状态和事实，不能拥有或修改比赛真相。引擎不是实时人机对战客户端，也不承载经营层职责。

## 2. 范围

**在范围内：**

- 单场完整比赛，包括常规节、必要时的加时和终场；
- 规则档案驱动的多联赛支持；
- 球员能力、倾向、球队组织和战术对比赛过程的可解释影响；
- 逐回合、逐阶段的因果与真实性评判；
- 确定性回放和可复现实验。

**明确排除：**

- 成长、选秀、交易、薪资和球队经营；
- 多人在线与实时对战；
- 玩家临场操控球员；
- 商业授权数据分发。

任何要改变范围的提案必须先修订本宪章，并在 `docs/decisions.md` 登记影响范围和取舍。

## 3. 目标层级

| 目标 | 定义 | 地位 |
| --- | --- | --- |
| **O1 真实** | 熟悉篮球的观察者难以从过程与结果区分模拟比赛与真实比赛 | 北极星 |
| **O2 干净框架** | 行为无隐藏剧本，状态有单一事实源，模块边界可验证 | O1 的必要条件 |
| **O3 可配置** | 同一内核可由档案表达不同球员、球队和联赛 | O1 的扩展面 |
| **O4 可评判** | 每个回合和阶段都有证据，缺陷能归因并可重现 | O1 的反馈环 |

O1 不能由单一综合分数直接证明。合法的逼近路径是同时建立 O2、O3 和 O4。

## 4. 宪章红线

### C1 · 无隐藏硬编码

影响行为的数值必须来自规则、档案或状态输入；公式可以在代码中表达，但其行为系数必须走受约束的数据通道。场上行为必须由球员输入、规则和比赛状态共同决定，禁止预编排的回合脚本和与输入无关的“让画面像篮球”分支。

### C2 · 评判落到过程

真实性判断必须覆盖回合和阶段。比分、命中率和其他原始聚合量只能作为 sanity net，不能单独证明过程真实。比赛级指数只能聚合已经产生的裁决，不能把未观测或证据不足当作通过。

### C3 · 物理与联赛语义分轴

人体运动、球飞行、碰撞和空间几何属于物理约束；计时、犯规、罚球、bonus、几何语义和阶段程序属于联赛规则。前者不能被联赛分支改变，后者必须由 `LeagueProfile` 参数化。切换联赛只能切换档案，不能复制一套引擎代码路径。

### C4 · 确定性

相同输入包和种子必须得到相同的事实事件序列和可比较的状态摘要。确定性是回放、评判、归因和校准的前提，而不是真实性本身。

## 5. 能力涌现

模拟行为的合法差异来源是：

```text
球员档案 + 球队/战术档案 + 联赛规则 + 比赛状态
                 ↓
          机会、意图、执行和裁决
                 ↓
              比赛过程
```

能力与倾向的维度、锚点和值语义由 `docs/attributes.md` 统一定义；球队组织和战术槽位由 `docs/tactics.md` 定义。任何新增维度都必须声明消费点、可观测响应和不可混淆的标定语义。

能力扰动测试是 C1 的机械守卫：在相同规则和状态下，改变单一输入应在相关机会、执行或结果上产生可解释响应；故意断开消费链时，测试必须失败。

## 6. 评判闭环

合法的改进循环是：

```text
生成事实 → 检查不变量 → 逐回合/逐阶段评判
       → 归因账本 → 规则/档案/能力通道改动
       → 确定性复验 → 再评判
```

闭环的最小要求：

1. 事件是事实，不是下游猜测；
2. 证据缺失、解析失败和不适用必须显式表达；
3. 每个缺陷带责任子系统和定位信息；
4. 校准改动能被固定输入重放，并能说明行为变化；
5. 参考分布有版本和来源，不能为让模拟通过而随意放宽。

## 7. 多联赛目标

首批档案覆盖 NBA、FIBA 和 NCAA 的计时、进攻时钟、犯规政策、罚球/bonus、几何和拥有权程序。档案的具体字段由 `docs/architecture.md` §6.3 定义，验收顺序由 `docs/protocol.md` 定义。

成功的多联赛切换必须同时证明：

- 核心模块没有联赛专用行为分支；
- 每个档案的程序边界有情景测试；
- 物理不变量和联赛语义分别被验证；
- 事件、回放和评判工件仍然完整。

## 8. 成功判据

一个阶段只有在以下证据同时成立时才可关闭：

1. L1 硬违反为零，且回合和阶段工件无遗漏；
2. 账本能从事件独立重建并对平；
3. 能力和战术扰动产生可解释响应，负面对照有效；
4. 参考分布只作为带版本的回归网，不能抵消硬门或证据缺口；
5. 至少一个完整校准循环有可复现实验包；
6. 规则、档案、状态和事件的责任边界通过结构守卫。

目标线、样本量和具体阶段门必须在版本化质量/协议文档中冻结；它们不能被历史快照或当前实测值隐式继承。
