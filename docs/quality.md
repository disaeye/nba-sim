# NBA-Sim · 质量与评判体系

> 定位：观测、检测、真实性评判与质量工件的规格，定义 L1/L2/L3 检测网、参考分布、sanity net、确定性和资源预算。
> 上游文档：`docs/charter.md`、`docs/architecture.md`、`docs/basketball.md`；过程验收见 `docs/protocol.md`。
> 实现状态和验证范围见 `docs/dev/status.md`；评判盲区与迁移任务见 `docs/dev/gap.md`。
> 修订纪律：本文档只定义观测语义和稳定质量门，不写当前实现快照、周期结果或执行命令。

## 0. 文档目的

本文档回答三个问题：

1. **如何检测偏差** —— L1 不变量、L2 回合评判、L3 阶段评判（§1–§2）；
2. **如何评判真实度** —— 参考分布、真实度指数、归因账本（§2.4–2.6）；
3. **如何闭环校准** —— 工具链、性能预算、确定性保证（§3–§5）。

阅读顺序：§1（L1 检测网）→ §2（真实度评判）→ §3（工具链）→ §4（性能预算）→ §5（确定性）。

## 1. 观测、不变量与真实度评判体系（P2 + P8）

"快速识别模拟偏差"只是半场；另一半是回答"这场像不像篮球、哪里不像、该动哪个子系统"。本章结构：

- **§1.1 L1 检测网**（每 tick 不变量）——抓"不可能"；
- **§2.1–2.3 真实度评判**（逐阶段、逐回合、归因账本）——抓"可能但不像"，宪章 C2 的实施；
- **§2.4 参考分布**——评判的基准是数据档案，不是代码；
- **§2.5 统计 sanity net**（批量聚合门）——降级为粗筛，不再是真实度裁决；
- **§5 确定性保证**——以上一切的前提。

### 1.1 L1 · Tick 不变量（引擎内，每 tick）

**目标**：捕获物理不可能 + 状态不自洽。

实现：`crates/invariants`，只依赖 `protocol`，校验每帧 `StreamTick`。

**集成要求**：每个发布 tick 都必须执行不变量检查；Hard 违反必须进入结构化工件并使调用方失败，Soft 违反可以计数但不得伪装为通过。

**严重级别**：`Hard`（物理不可能）/ `Soft`（不合理但可能合法，计数上报不阻断）。`Violation` 结构必须携带 `severity` 字段。

**工件输出**：违反必须写入 `violations.ndjson`（`{tick, rule, severity, detail}`），作为偏差分类账（§3.3）与 debug-server 违规时间轴的数据源。**禁止只写 stderr。**

**单一事实源**：限值一律取自帧内 `FrameRules`（来自 `GameRules`）。任何离线审计工具不得自带限值副本——复用 invariants crate 的 Rust 审计 CLI。`frame.rules` 为必填字段。

**阶段语义**：L1 规则必须定义 DeadBall、InboundSetup、FreeThrow 等阶段的适用性和豁免（帧应携带足够的生命周期语义）：

- 发球人按规则站**界外**，球被移到界外发球点——`PLAYER_IN_BOUNDS` / `BALL_SPEED` 等规则需要阶段豁免或替代判定，否则必然误报；
- **禁止投影规避**：不得通过导出帧时隐藏事实来迎合不变量（如 InboundReady 期间不导出持球者）——违反"事件即事实"（architecture.md §7.3）。正确做法是不变量认识发球阶段并改判定，而不是帧撒谎；
- 任何离散站位重置都必须由显式生命周期事实标记，并由检查器按阶段解释，不能隐藏在投影层。

## 2. 真实度评判（宪章 C2 实施）

### 2.1 L2 · 回合评判（每回合结束）

**目标**：捕获叙事断裂，并回答"这个回合像不像真实篮球"（宪章 C2）。

每个回合结束时产出**裁决**（`PossessionVerdict`），逐条写入 `judgments.ndjson`。准则分两类：

**(a) 结构因果**：

- 每次 `Shoot` 的 `contest_intensity` 必须与"出手瞬间最近防守者距离"一致（容差内）；
- 每次成功传球的接球人，在到达时刻必须在传球走廊可达范围；
- `STEAL` 事件中抢断者必须在传球走廊上；
- 回合时长 ∈ [1 tick, 24秒+进攻篮板延长时间]：篮球没有"规则最小"回合时长（发球即被抢断可 <1 秒），下界只是零/负时长的异常性检查；
- **因果链完整**：每次得分有来源，每次失误有归因，每个篮板有卡位与落点；结果事件指向决定它的飞行、接触、封盖或触筐事实。
- **动作完整**：每个已开始动作有完成、取消或失败；取消和失败带原因。
- **责任完整**：每次换防、协防、补位和回位能找到触发人、原责任人、接替人和结束条件。
- **罚则完整**：个人犯规、球队犯规、离场、罚球次数和球权恢复能按事件顺序重建。

**(b) 真实度清单**（对照参考分布 §2.4）：

- **节奏**：回合时长 × 结果（得分/打铁/失误）组合是否落在真实分布内；
- **动作构成**：传球数、突破数、出手类型构成对照同结果类回合的分布；
- **出手质量**：出手难度（contest）× 出手者能力的匹配度——低能力者频繁强投高难度、完全空位却反复传导错过出手，都是缺陷条目；
- **时钟利用**：进攻时钟末段与节末的出手选择合理（有 20 秒却立即仓促出手、无压迫却耗到鸣笛，都是缺陷条目）。

每条准则输出 `{criterion, verdict, severity, detail, attribution}`；`verdict` 必须能表达 Pass、Defect、NotApplicable 和 InsufficientEvidence。缺陷条目带责任子系统（§2.3）。

### 2.2 L3 · 阶段评判（阶段转换时）

**目标**：宪章 C2 的"逐阶段"实施。`SubPhase` / `GameFlowState` 的每次转换产出裁决：

- **转换合法性**：只允许状态机允许的迁移（`architecture.md` §3.3 转换表与 flow 转换），不得无因跳变；
- **时间合理性**：各阶段停留时长必须符合规则档案和带版本的质量 fixture，阈值不得来自代码常数；
- **参与者一致**：转换后参与者（持球人、出手者、发球者）与球状态自洽（如 FreeThrow 阶段必须有且只有一名罚球者与合法站位）。

阶段裁决与回合裁决汇入同一评判账本；阶段缺陷通常归因引擎编排层（转换逻辑）或决策层（异常停留）。

### 2.3 真实度指数与归因账本

**真实度指数**：回合裁决与阶段裁决的加权聚合。聚合的是**裁决结果**，不是比分/命中率这类原始结果——这是宪章 C2 允许的唯一统计形式。指数是"缺陷收缩趋势"的跟踪量，不是唯一裁决；真实度的判断权在逐条准则。

**归因账本**：每条评判准则在定义时预声明责任子系统：

| 准则族 | 责任子系统 |
| -------- | ----------- |
| 出手选择 / 动作构成 / 节奏 / 时钟利用 | decision |
| 空间 / 位移 / 接触几何 | physics（+ semantics 解释） |
| 犯规种类 / 罚则执行 / 违例程序 | officiating（+ semantics） |
| 防守责任交接 | decision + tactics |
| 阶段停留 / 转换合法性 | engine 编排 |
| 得分 / 时钟 / 球权因果 | engine + invariants |

跑批后聚合为 **(准则 × 子系统 × 频次 × 严重度)** 账本（`attribution_report.json`）：频次最高的缺陷准则就是本轮校准目标。**"模拟与真实相去甚远"从此是一个可归因的缺陷清单，而不是一种感觉**——这就是反馈闭环（protocol.md §1）的输出接口。

**工件**：`judgments.ndjson`（一行 = 一个回合/一次阶段转换的一条准则裁决）+ `attribution_report.json`。batch 模式必须与 violations 一起写入（§3.3）。

### 2.4 参考分布：数据档案

真实度准则需要参照系，参照系必须是**数据，不是代码**（宪章 C1）：

- **内容**：真实比赛的回合级分布——时长×结果、传球数、出手类型构成、每回合得分（PPP）、失误率、罚球率、按防守距离的出手占比等；
- **形态**：基于篮球常识的手工 fixture（按联赛维度分套：NBA/FIBA 规则下的分布不同），与 `GameRules` 走同一 JSON 覆盖通道；
- **扩展位**：fixture 结构是分布描述（直方图/分位数）；接入更高质量的 play-by-play 数据时替换数据档案，评判代码不改；
- **纪律**：fixture 变更属于校准行为，走 protocol.md §1 协议附证据；fixture 不参与引擎运行、不影响黄金哈希，但影响评判结果，因此必须带版本号；
- **盲区登记**：任何有限准则集都是真实比赛分布的低维投影。评判器侧的准则盲区由 `crates/evaluator/fixtures/blind_spots.md` 登记并随准则扩展逐轮收缩；物理与接触模型的数据缺口由 `docs/blind_spots.md` 登记。两份清单都不允许把「进带」误读为「覆盖」。

### 2.5 统计 sanity net（批量聚合门）

**定位**：全场总分、回合数、时长等聚合统计保留**目标带 + 阶段门**结构，但职责降级为 **sanity net**——只粗筛"错得离谱"，**不再是真实度的裁决**（宪章 C2：正确的总分可以由无数种错误的过程拼出）。真实度判断权在 §2.1–2.3 的逐回合/逐阶段评判。

- 批量运行版本化的种子矩阵，聚合每场统计到 JSON；
- 指标：比分分布、**投篮分解（2分/3分命中率、罚球率）**、失误率、回合时长分布、球员速度 p50/p99；
- 与目标带或阶段门对比，漂移超带 → CI 失败。

**基线锚定原则**：基线用于奖励逼近目标、惩罚偏离目标；参考带必须来自独立设计或数据来源，不能由当前模拟输出反推。结构是目标带与阶段门：

```
目标带和阶段门必须由带版本的 fixture 提供；质量规格只规定门的语义：目标带代表长期目标，阶段门代表收敛走廊，历史门不再作为当前门。
```

> 具体数值必须由带版本的质量 fixture 单独管理；修改目标带或阶段门属于校准变更，必须遵循 `docs/protocol.md` 的基线、证据和阈值独立性要求。

**判定口径**：总分取 p50，回合数与回合时长取均值；样本量、置信范围和 fixture 版本必须随报告记录。

规则：统计落在当前门内才通过 sanity net；越出门外即报警；推进门必须保留旧门作为历史证据，不能用当前实测值的任意百分比反推新基准。

## 3. 观测与调试工具链

检测体系没有工具链就是空话。以下为可执行验收的组成部分：

### 3.1 批量跑批 CLI

目标形态：

```
nba-sim --rules rules.json --seeds 0..20 batch --out stats.jsonl
```

- `--rules`：部分 JSON 覆盖 `GameRules`（依赖 `#[serde(default)]`），**校准的唯一入口**（P6）；
- `batch`：种子矩阵批量跑、每场输出一行统计 JSON；
- 跑批必须 release 模式（见 §4 性能预算）。

### 3.2 评判器（回合/阶段评判与归因）

（准则内容即 §2.1–2.3。）工具形态为独立 analyzer/evaluator：读 ndjson 流 + PossessionSummary + 参考分布 fixture（§2.4），输出 `judgments.ndjson` 与归因报告（§2.3）。

### 3.3 violations 工件

`violations.ndjson` 每行 `{tick, rule, severity, detail}`；analyzer 按 `rule` 聚合计数排序——80% 的"不像篮球"通常来自 2–3 个根因，分类账就是找根因的第一站。

### 3.4 debug-server 违规时间轴

回放 UI 加违规时间轴：加载 violations.ndjson，违规帧打点，点击跳转到该 tick 看场上态势。物理问题几乎都能 3 秒肉眼看出来，前提是违规检测先建好。

### 3.5 评判工件与归因报告

- `judgments.ndjson` / `attribution_report.json`（§2.3）由评判器产出；**batch 模式必须与 violations 工件一起写入**；
- 归因报告按 (准则 × 子系统) 排序输出 top 缺陷——校准选题从"感觉哪里不对"变成"账本第一行"；
- 校准 PR 必须附改动前后的归因报告 diff（真实度指数变化 + top 缺陷准则收缩），否则 protocol.md §1 证据不全。

## 4. 性能预算

性能是验收项，不是事后优化。

### 4.1 预算表

| 指标 | 预算 | 验证方式 |
| --- | --- | --- |
| release 模式吞吐 | 由已批准的基准 fixture 冻结；节间开场球权程序落地后空闲复测 seed42 = 6530 ticks/s，seed1 = 6365 ticks/s（scripts/perf_fixture.json，`scripts/check_perf_fixture.py` 已接入 `run-tests.sh` 后置门，失败计入退出码） | 分层 benchmark 工具 |
| 单节运行时间 | 由已批准的基准 fixture 冻结 | 分层 benchmark 工具 |
| 每 tick 堆分配 | 稳态为 0（复用缓冲；`build_tick` 的 Vec/String 复用） | 分配计数器或 heaptrack 抽查 |
| `String` clone / tick | 消除（球员 id/jersey 预分配 Arc/静态） | 代码审查 + 分配计数 |
| 批量跑批 | 由资源预算 fixture 冻结 | batch 资源报告 |
| 测试套件执行 | tier1 ≤ 2 分钟；tier2 ≤ 6 分钟；tier2+3 ≤ 15 分钟；全量 ≤ 20 分钟（4 核 3.7GB 参考机，`scripts/run-tests.sh` 分层实测：tier1 62s、全量 945s）；单目标不得无界挂起（`par_test.py --timeout` 600s 硬上限） | `scripts/run-tests.sh` 分层计时 |
| 测试并行调度 | 两级并行：目标间（`par_test.py --jobs`）× 目标内种子间（rayon `par_iter`，在 `fingerprint_for_setup` 与各测试的多 seed 循环）；内存大户 `stats_baseline` 串行独占 | `par_test.py --serial` 默认值 |

### 4.2 纪律

- 性能优化 PR 不得改变行为——黄金哈希必须不变（哈希输入不含渲染舍入字段，纯数据结构优化的哈希天然稳定）；
- 若优化涉及浮点求和顺序等哈希敏感路径，须在 PR 中说明并重冻结哈希。

## 5. 确定性保证（一切检测与评判的前提）

- 固定步长 `FixedDt`、固定种子 `ChaCha8Rng`、禁止 `HashMap` 迭代序影响逻辑（所有迭代先排序）；
- **黄金 tick 哈希**：对标准种子运行，把每 tick 关键字段哈希串联，进 git。任何改动导致逐 tick 分歧 → CI 立即暴露；
- 黄金哈希抓"变了"，评判账本抓"不像"，sanity net 抓"错得离谱"。三者互补，缺一不可。

## 6. 能力扰动测试（P7 · 宪章 C1 的机械守卫）

**设计要求**：

1. **能力是行为差异的唯一合法来源**：同规则同状态下，两个球员的行为差异只能来自能力向量与倾向。决策效用（architecture.md §5.1）、物理上限调制、采样个性化、裁决结算的输入都必须是 `(能力, 规则, 状态)`；
2. **禁止剧本化行为**：预编排的回合脚本、"X 情形必做 Y"式与能力无关的经验分支、写死的角色套路，全部属于行为硬编码（宪章 C1）。战术倾向只能用倾向/能力参数表达，不能用代码分支表达；
3. **能力扰动测试（机械守卫，常驻回归）**：扰动某球员单维能力（上/下），引擎可观测行为必须**单调响应**——如 `shooting_three` 影响三分出手占比与命中率、`steal` 影响抢断尝试与成功率、持球决策维（`attributes.md` §2.5，v2 `decision_iq`）影响低质量出手率与助攻失误比。**无响应 = 该行为路径是死的（脚本或常数短路）= 违反 C1**。

**验收**：每个能力维度至少一条可观测的行为响应链，且扰动测试含负面对照（故意断路一条链，测试必须红）（protocol.md §2.1 M9）。
