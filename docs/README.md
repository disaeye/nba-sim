# NBA-Sim 文档体系

> 本文档规定内容的归属、权威性和生命周期。它不是比赛设计，也不是开发状态报告。

## 0. 先回答“我正在读什么”

本仓库把文档分成三个相互连接、但不互相冒充的面：

| 面 | 回答的问题 | 真值来源 | 是否有完成态 |
| --- | --- | --- | --- |
| **规格面** `docs/*.md` | 系统应该是什么、什么行为被允许 | 项目批准的设计 | 没有；持续修订 |
| **决策面** `docs/decisions.md` | 为什么在多个方案中选择这一方案 | 已批准或待批准的取舍 | 决策可被 supersede |
| **工作面** `docs/dev/` | 现在实现了什么、下一步做什么、证据是什么 | 代码、测试和可复现实验 | 有；完成后归档 |

同一事实只能有一个权威归属：

- “应该采用什么规则”进入规格面；
- “为什么选这个规则”进入决策面；
- “代码是否已经做到”进入工作面；
- “哪一次运行观察到了什么”进入证据或周期归档。

## 1. 规格面目录

```text
docs/
├── README.md          ← 文档治理规则
├── charter.md         ← 愿景、范围、红线与成功判据
├── decisions.md       ← 跨模块设计决策、理由与开放决策
├── architecture.md    ← 分层、数据流、状态机与模块边界
├── quality.md         ← 不变量、评判、确定性与质量工件
├── attributes.md      ← 球员/球队输入的分类学和值语义
├── tactics.md         ← 阵容、战术、适配与教练输入规格
└── protocol.md        ← 校准、证据包和验收过程规格
```

规格文档应该能脱离某个工作区快照独立阅读。它可以引用稳定的类型、事件和接口名称，但不能把某次测试的数字、某个轮次的结果、命令输出或当前缺口写成设计前提。

### 1.1 规格职责

- `charter.md` 只决定目标、范围和不可放宽的红线；
- `architecture.md` 只决定系统如何分层、事实如何流动和状态如何转移；
- `quality.md` 只决定如何观测、发现违反并表达证据缺口；
- `attributes.md` 只决定输入维度和值的语义；
- `tactics.md` 只决定球队组织与战术档案如何向决策层提供机会；
- `protocol.md` 只决定如何校准、如何验收和如何形成证据包；
- `decisions.md` 记录跨文档的取舍，不重复完整规格。

当两份规格发生冲突时，先按 `charter.md` 的红线裁决，再按职责边界裁决；不能用当前代码或历史记录悄悄改写规格。

## 2. 工作面目录

```text
docs/dev/
├── README.md                         ← 工作面入口和生命周期规则
├── status.md                         ← 唯一当前状态快照
├── gap.md                            ← 跨周期差距程序与依赖图
├── roadmap.md                        ← 里程碑路线，不记录完成度
├── current/
│   └── plan.md                       ← 当前唯一活跃实施计划
├── evidence/
│   ├── problem.md                    ← 原始问题与复现实验
│   └── impact_assessment.md          ← 跨周期伤害评估
└── cycles/
    ├── 20260901_historical/          ← 更早周期快照
    └── 20260911_first-principles/    ← 已结束周期的方案与执行记录
```

`current/` 只保留一个当前计划入口 `plan.md`，其中每项都必须是未完成工作。计划一旦只剩历史结果，就随周期移入 `cycles/`；不在 `current/` 留“已完成但方便查找”的副本。

## 3. 工作面内容分工

| 内容 | 唯一归属 | 允许写什么 | 不允许写什么 |
| --- | --- | --- | --- |
| 当前状态 | `dev/status.md` | 当前代码、测试、守卫和开放门 | 设计推导、长篇执行流水账 |
| 当前待办 | `dev/current/plan.md` | 未完成任务、依赖、验收条件 | 已完成轮次的详细叙述 |
| 跨周期程序 | `dev/gap.md` | 差距类别、依赖、出口条件 | 当前门状态、逐次命令输出 |
| 里程碑路线 | `dev/roadmap.md` | M1–M10 的稳定顺序和边界 | “M9 已完成”之类的状态断言 |
| 原始证据 | `dev/evidence/` | 输入、命令、输出、失败和口径 | 把历史结果概括成当前真相 |
| 周期记录 | `dev/cycles/` | 方案版本、执行过程和当时结论 | 继续作为当前计划入口 |

状态文件可以引用证据文件；计划可以引用规格和状态；规格不依赖状态才能成立。工作面中的设计提案只有在登记为 accepted 决策并吸收到对应规格后，才成为稳定规范。

## 4. 机械治理

`scripts/check_docs.py` 是文档引用和基本纪律的唯一守卫。它必须能够：

1. 解析带路径的引用，而不是只按 basename 猜目标；
2. 对同名文件的模糊引用报错；
3. 检查章节号确实存在；
4. 检查规格面没有日期、实测/完成度结果和可执行命令；
5. 检查工作面没有空文档。

引用优先使用仓库根相对路径，例如 `docs/dev/status.md §2`。只有在目标 basename 唯一时，才允许使用 `status.md §2` 这种短写法。

## 5. 阅读路径

- **了解项目**：`charter.md` → `decisions.md` → `architecture.md` → `quality.md` → `attributes.md` / `tactics.md` → `protocol.md`；
- **准备改引擎**：规格面相关文档 → `docs/dev/status.md` → `docs/dev/current/plan.md`；
- **追溯证据**：从 `status.md` 的证据链接进入 `evidence/` 或对应 `cycles/`，不要反过来把归档快照当状态入口；
- **审查文档结构**：先读本文档，再读 `docs/dev/README.md`。

## 6. 变更规则

1. 新增稳定规则时，先确定它属于哪份规格，避免把同一段完整设计复制到多份文件；
2. 新增跨模块取舍时登记 ADR，并在规格中只保留被接受的结论；
3. 代码实现变化先更新 `dev/status.md` 和必要证据，不为迁就代码而改写规格；
4. 计划完成后立即归档，当前入口只保留下一项未完成工作；
5. 删除或移动文档时，必须同时更新路径引用并运行文档守卫；
6. 历史文件可以保留错误结论，但必须明确其周期和非权威属性。
