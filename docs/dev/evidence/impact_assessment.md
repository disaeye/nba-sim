## 1. #15 F5：战术与防守零影响（最严重）

### 实测证据

**防守侧（决定性证据）**：同一 seed、同一阵容，只改 `defense_tactic`，逐 tick 对比全部 23,845 帧，
**唯一不同的字段是展示字符串** `defensive_tactic`，其余（位置、球、比分、事件、决策 trace）完全一致：

```text
共 23845 tick，差异字段统计：
   defensive_tactic       23845      ← 仅此一项
   （其余字段差异均为 0）

tick 0 field=defensive_tactic
     A: "保守人盯人 (Conservative Man)"
     B: "大量换防 (Switch Heavy)"
```

8 seed × 5 方案的聚合统计也完全相同：

```text
scheme                     pts    poss     3PA%      TO%       FT       FGA
def_man_conservative      54.1    65.0      86%      42%      5.0      27.6
def_man_pressure          54.1    65.0      86%      42%      5.0      27.6
def_switch_heavy          54.1    65.0      86%      42%      5.0      27.6
def_drop_coverage         54.1    65.0      86%      42%      5.0      27.6
def_hedge_recover         54.1    65.0      86%      42%      5.0      27.6
```

（注：事件流哈希会因展示字符串而不同，所以"哈希不同"不能作为防守生效的证据；
必须逐字段比对。本轮先用哈希判断，得出过"方案有影响"的错误中间结论，随后逐字段比对纠正。）

```text
scheme=def_man_conservative score=27-15 poss=59 ball=Dead{pos:(67.99,13.x)}
scheme=def_man_pressure     score=27-15 poss=59 ball=Dead{pos:(67.99,13.x)}
scheme=def_switch_heavy     score=27-15 poss=59 ball=Dead{pos:(67.99,13.x)}
scheme=def_drop_coverage    score=27-15 poss=59 ball=Dead{pos:(67.99,13.x)}
scheme=def_hedge_recover    score=27-15 poss=59 ball=Dead{pos:(67.99,13.x)}
```

**进攻侧**：`TacticalSet::from_id` 声明支持 6 个 id，但 `TacticalSetSpec::builtin`（引擎实际加载入口）只认 2 个，其余 4 个直接 `panic`：

```text
offense=off_horns_pnr       score=32-17 poss=64   ← 可用
offense=off_motion_spacing  score=35-20 poss=64   ← 可用
offense=off_transition_push PANIC: invalid match setup
offense=off_delay_attack    PANIC
offense=off_post_split      PANIC
offense=off_drag_screen     PANIC
```

**代码侧**：`DefensiveTactic` 的枚举在 `match_engine.rs` 里只被用于生成展示字符串 `defensive_tactic_name()`，物理层与决策管线**从不消费**它。

```text
grep "DropAndContain|HedgeAndRecover|SwitchAssignment" crates/engine/ crates/physics/ → 空
grep "fn slot_fill|fn fitness|fn match_slots" crates/ → 空
```

### 伤害

- **这是"播放动画"而非"打篮球"**：教练、战术、防守方案全部是装饰。用户改档案得不到不同过程，直接违反 gap.md §21.2。
- **误导性最强**：系统会输出 `defensive_tactic: "def_switch_heavy"` 等字段，让消费者以为防守体系在起作用。
- **能力系统也被架空**：`defense_perimeter` / `defense_interior` / `decision_iq` 等维度缺少真正的下游消费者（部分只进犯规率或效用系数）。
- 依赖 #14（World 私有化）才能安全重构，所以 #14 的"低伤害"只是因为它挡着 #15。

## 2. #11 F3：真实度严重失真

### 实测证据（seed 42 full scope）

| 指标 | 模拟 | 真实 NBA | 偏差 |
| --- | ---: | ---: | --- |
| 3P 命中率 | **64.7%** | ~36% | 1.8× |
| 2P 命中率 | 63.6% | ~54% | 1.2× |
| FT 命中率 | 85.0% | ~78% | 1.1× |
| **3P 出手占比** | **81%** | ~40% | 2.0× |
| 出手距离中位数 | 29.8 ft | ~13 ft | 2.3× |
| 回合数 | ~270 | ~200 | 1.35× |
| 犯规事件 | 14 | ~40 | 0.35× |
| 罚球出手 | 16 | ~45 | 0.36× |

出手位置分布（seed 0，100 次出手）：

```text
篮下(<10ft) 4    中距(10–23.75ft) 12    三分(>=23.75ft) 84
```

### 回合终端分布（seed 0，281 回合）

```text
TURNOVER_VIOLATION     117   41.6%   ← 真实 NBA 约 12%
SCORE                   73   26.0%   ← 真实约 45%
TURNOVER_STEAL          31   11.0%
TURNOVER_PASS_TIPPED    25    8.9%
DEFENSIVE_REBOUND       24    8.5%   ← 真实约 33%
```

违例细分：`SHOT_CLOCK_VIOLATION 38`、`FIVE_SECOND_INBOUND 20`、`EIGHT_SECOND_BACKCOURT 10`。

### 伤害

- **统计输出不可用于分析**：任何基于模拟数据的战术研究、球员评价、分布对比都会得到错误结论。
- **41.6% 回合以违例终结**说明决策-执行链在压力下普遍失败（不是罕见边界情况），即核心行为逻辑不成立。
- **`DEFENSIVE_REBOUND` 仅 8.5%**（真实 33%）说明"投失后由防守方拿下"这一最基本的篮球事件链大部分没走通，反映终结/篮板环节存在系统性缺陷。
- 这是**最难的一项**：它不是"补齐缺失功能"，而是需要建立"目标带 + 归因账本 + 参数化校准"的完整闭环，且每轮校准都要 A/B 与种子矩阵取证。

## 3. #10 F2.2：证据模型让缺陷隐形

### 实测证据

当前真实度指数计算：

```text
指数 = 1 - 13.75/1394.00 = 0.9901
其中 Soft 准则的 PASS 占了分母 765 条
```

因为这 5 场里 1994 条裁决中只有 40 条缺陷，**指数稳定在 0.99**，给人"基本完美"的错觉——而同一批数据里 3P% 是 64.7%、81% 的回合以三分出手、41.6% 回合违例。

同时：

- `Judgment` 只有 `Pass` / `Defect`，**没有 `NotApplicable`**，导致"不适用"被算成"通过"（例如罚球得分对 `CONTEST_CONSISTENCY` 本不适用，此前被算成 Hard 缺陷，是另一方向的错误）。
- **没有 `InsufficientEvidence`**：证据不足时无法表达，只能二选一。
- 无固定分母（opportunities/passes/defects/insufficient），无法识别"这条准则其实只覆盖了 3 个样本"。

### 伤害

- **判断力被污染**：它不制造错误，但**掩盖错误**。没有它，我会更早发现 #15 和 #11。
- 依赖关系上，它是 #11 的前置：分母不对，校准就失去度量。所以它虽不直接伤害模拟，却是**修复路径上的必经关卡**。
- 反过来说：如果时间只够做一件事来提升"我能发现问题"的能力，就做这个。

## 4. #12 / #13：调试与审计能力缺失

### #12 F4.1 事件 ID

- `FrameEvent` 有 `sequence`，但没有稳定 `event_id` / `parent_event_id`。
- **实测后果**：本轮排查 `PLAYER_SPEED` 时，我只能靠"前后打印帧 + 人工比对"定位，无法从一条缺陷直接跳到它的因果父事件。problem.md 里多次出现"需检查事件窗口配对"这类模糊结论，根因就是缺 ID。
- 伤害等级中：**不改变模拟结果，但显著抬高排错成本**，并让评审无法给出可操作证据。

### #13 F4.2 回合账本

- 无 `PossessionLedgerEntry`、无 `PossessionEndCause` 穷举、无 gap.md §7.5 的四个平衡式。
- **实测后果**：本轮发现 `box_score.fouls` 字段**从未被写入**（`grep "fouls +=" → 0 处`），CLI 一直打印 `Fouls: 0`，而事件流里有 14 次犯规。这个错误能存活至今，正是因为**没有任何账本在对平**。
- 伤害等级中：**让统计错误长期潜伏**。与 #11 是共生关系——账本缺失使校准无法验证。

## 5. #14 F4.3：低直接伤害，但阻塞最严重项

- `MatchEngine` 的全部真相字段仍是 `pub`（`possession`、`carrier_idx`、`ball_state`、`home_score`…）。
- 本轮未观察到"外部写坏状态"的实际事故；作为库被误用的风险存在，但当前唯一消费者是自家 CLI/UI。
- **真正的伤害是间接的**：不完成私有化，就无法安全地把 `carrier_idx` 索引绑定替换为能力适配 slot fill（#15），因为替换需要一个稳定的只读 World 接口作为契约。
- 所以它必须排在 #15 之前，但自身优先级低。

## 7. 建议的处置顺序与理由

```text
1. #10 F2.2  证据模型    ← 先恢复"发现问题的能力"，否则后面每步都无法验证
2. #13 F4.2  回合账本    ← 建立对平检查，把潜伏统计错误逼出来（已抓到 fouls=0）
3. #12 F4.1  事件 ID      ← 让缺陷可定位到因果链，降低后续所有排错成本
4. #14 F4.3  World 私有化 ← 为战术重构提供安全接口
5. #15 F5    战术/防守执行 ← 修复"零影响"，这是"能打篮球"的核心
6. #11 F3    真实度校准   ← 依赖 1/2/5 全部到位后才可能真正收敛
7. #20 F7    验收重跑     ← 最后执行
```

**关键依赖说明**：表面看 #11（真实度）伤害最大，但**现在做校准是无效的**——因为在防守零影响、41.6% 回合违例、账本缺失的条件下，调参只是在拟合一个错误的过程。这与我在 `fix_plan.md` 里写的"F2.2 必须先于 F3"是同一个判断，本轮实测进一步强化了它。

## 8. 一句话总结

当前引擎**能生成可信的过程，但生成的不是篮球**：物理与规则是干净的，战术与防守是装饰，统计分布与真实篮球相差 1.4–7.6 倍。最危险的不是这些缺陷本身，而是 `realism_index = 0.99` 把它们包装成了"基本完成"。
