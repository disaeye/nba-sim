# NBA-Sim · 跨周期差距地图

> 文档类型：跨周期工程程序与依赖地图。
> 权威边界：稳定语义由 `docs/*.md` 契约定义；当前实现由 `docs/dev/status.md` 定义；原始运行证据由 `docs/dev/evidence/` 和周期归档保存。
> 本文档只回答：哪些目标尚未形成可证明实现、它们如何依赖、什么条件可以关闭差距。
> 本文档不是当前状态快照、执行日志或参数结果表。

## 0. 使用方式

差距条目必须同时指向：

1. 上游稳定规格；
2. 需要补齐的结构或证据；
3. 可机械判定的出口条件；
4. 当前状态和证据的入口。

“实现了一个类型”“某个 seed 通过”或“有一条代码路径”都不能单独关闭差距。当前是否关闭，以 `docs/dev/status.md` 的门矩阵为准；本文件只保存跨周期可复用的程序结构。

## 1. 优先级与差距分类

### 1.1 差距分类

| 类别 | 需要闭合的对象 | 失败后果 |
| --- | --- | --- |
| 状态与因果 | 权威时间、球态、生命周期、事件和账本 | 任何统计和回放都不可相信 |
| 物理与规则 | 运动上限、空间事实、语义和联赛程序 | 过程可能不合法或无法解释 |
| 决策与行为 | 机会、意图、执行重校验和能力消费链 | 模拟成为固定脚本 |
| 组织与档案 | 战术、对位、防守责任、轮换和 profile | 配置只能改变标签或展示 |
| 评判与证据 | 固定分母、证据状态、归因和参考 fixture | 绿色指数掩盖缺陷 |
| 工具与资源 | 确定性、manifest、流模式、资源预算和守卫 | 结果无法复现或验证无法运行 |

### 1.2 处理优先级

```text
状态与因果
  > 物理与规则合法性
  > 可解释的行为差异
  > 参考分布拟合
  > 性能与存储
  > 展示与便利
```

后层工作不得用结果掩盖前层缺陷。特别是：

- 统计进入参考带不能替代因果和机制证据；
- 黄金哈希只能证明确定性和变化可追踪，不能证明真实度；
- 评判器的证据不足不能被编码成 Pass；
- 展示层不得拥有比赛真相。

## 2. 差距关闭的共同门

每项差距都应按以下门顺序关闭：

1. **结构门**：类型、责任边界和单一事实源清楚；
2. **机制门**：输入扰动确实经过机会、执行或裁决链；
3. **观测门**：事实、事件、评判和账本能定位变化；
4. **反事实门**：断开消费链时回归必须失败；
5. **重放门**：固定输入和规则档案可以重建结果。

任何一门未满足，只能标记为部分关闭或证据不足。

## 4. 生命周期、时间和离散布置

### 4.1 权威时间

权威时钟必须使用可精确比较的整数 tick 或整数微时间。显示用浮点数是投影，不能成为回合时长或阶段合法性的来源。节间、罚球、发球和终场都必须有明确的时间推进规则。

### 4.2 生命周期边界

宏观生命周期和回合子阶段必须正交。每个阶段声明可写事实、输入和出口；短路必须以显式结果表示，不能由散落的提前返回隐式改变比赛程序。

### 4.3 离散生命周期事实

发球布置、换人入场、节间站位和其他离散位置重置必须发布结构化的生命周期事实，例如 `PlacementStarted` / `PlacementApplied`，并由检查器按事实解释。不能通过隐藏球员、伪造速度或删除帧来规避不变量。

**出口条件**：所有离散位置变化都能定位到生命周期事实；连续运动检查与离散布置豁免不混淆；异常路径仍能进入明确终态。

## 5. 球权与球运动迁移

### 5.1 正交状态目标

球权归属与球的运动是两个维度：

```rust
enum BallControl {
    Controlled { player_id: PlayerId, team: TeamId },
    Uncontrolled { last_touch_team: Option<TeamId>, last_touch_player: Option<PlayerId> },
    Dead { reason: DeadBallReason, next_team: Option<TeamId> },
}

enum BallMotion {
    AtPlayer { player_id: PlayerId, offset: Vec3 },
    Carrying { player_id: PlayerId, offset: Vec3 },
    Flight(FlightParams),
    Loose(LooseBallParams),
    Stationary { position: Vec3 },
}
```

外部可以保留稳定的 `BallState` 接口，但内部不得让轨迹字段再次承担归属真相。`holder`、`possession_team`、`is_live` 和位置都应是派生视图或明确载荷。

### 5.2 唯一状态转移

所有传球、投篮、抢断、篮板、出界、罚球和发球边都必须经过唯一的状态转移通道。状态转换函数接收当前状态与已发生事实，返回新状态和事件；普通调用路径不能直接改写旁路字段。

### 5.2a 无持球人球态的归属语义（ADR-010）

ball handler 是球态的函数，不是独立可写字段。无持球人球态（`ControlTransfer` /
`LooseBall` / `RimRebound` / `Dead`）下 handler 派生为 `None`，由读取方显式处理，
不得用名单下标投影出占位 handler；team possession 是独立派生量，由 `last_touch_team`
决定，不因无 handler 而消失。逐球态的 handler / possession 裁定表见 `docs/decisions.md`
ADR-010（accepted）。该裁定否定了旧 `carrier_idx` 回退 `roster[possession][idx]`
（违反 ADR-005），是删除 `carrier_idx` 的前提。

### 5.3 状态边完整性

状态机必须列出合法边、非法边和每条边的责任事件。非法边在领域层拒绝；没有足够事实时输出证据不足或完整性失败，不静默选择一个看似合理的状态。

## 6. 主循环和写权限

### 6.1 固定阶段序列

目标顺序为：时钟与生命周期 → 运行时约束 → 动作窗口 → 条件性罚球/决策 → 执行重校验 → 物理 → 弹道裁决 → 语义 → 裁决 → 阶段转换 → 不变量 → 快照输出。

### 6.2 阶段写权限

阶段函数只接收完成职责所需的窄参数。时钟阶段不能写比分，感知阶段不能写世界，快照阶段不能产生副作用，不变量阶段不能修复事实。需要改变该边界时，必须登记跨模块决策。

### 6.3 生命周期完备性

每个比赛开始、活球、死球、罚球、发球、节末、加时和终场边界都必须有进入条件、退出条件、责任事件和超时处理。不存在依赖 tick 上限才能结束比赛的正常路径。

## 7. 事件、动作和账本

### 7.1 事件封装

事实事件必须具备版本化 kind、全场稳定 `event_id`、tick/sequence、责任主体和必要的上下文。因果关系用可验证的 `parent_event_id` 表达，而不是让评判器按字符串或相邻帧猜测。

### 7.2 动作生命周期

传球、投篮、突破、掩护、协防和换人按 `docs/basketball.md` §2 表示开始、执行、完成、取消和失败。动作事件不能预先宣称尚未发生的结果；结果事件必须由物理或裁决事实触发。

### 7.3 回合生命周期

每个回合有显式开始、连续的 `possession_id`、合法终端和下一回合关系。回合摘要是账本投影，不是另一个可写事实源。

### 7.4 回合时长

回合时长由权威 tick 差值计算。进攻篮板延长、罚球停表、节末和死球等待必须按规则档案分别处理；显示层不得用正数下限伪造时长。

### 7.5 账本平衡

至少维护并独立检查：

- 得分：事件得分增量 = 合法得分结果；
- 球权：终端原因、控制转移和新回合起点相互匹配；
- 时间：阶段/回合时间片能重建比赛时钟；
- 犯规：个人、球队、罚则和相关程序相互匹配。

无法归因的终端必须使完整性门失败或明确产出 `InsufficientEvidence`，不能成为正常通过样本。

## 8. 质量检测网

### 8.1 L0：协议完整性

解析失败、版本不兼容、缺失 manifest、缺失事件身份和不完整字段必须显式失败。不同流投影应声明它们是否包含几何、因果或仅摘要信息。

### 8.2 L1：硬物理与状态不变量

每个发布 tick 都检查球速、球员速度、球人距离、位置边界、时间/比分单调性和球态一致性。规则阈值从帧内规则事实或规则档案获得；阶段豁免必须有生命周期依据。

### 8.3 L2：事件因果和账本

每个得分、失误、篮板、罚球、回合终端和关键动作都必须能沿事件父链定位。传球的冻结落点、实际落点和接球事实必须有明确关系；运动估计偏差与因果断裂应分开计量。

## 9. 决策：机会—意图—执行

### 9.1 感知快照

感知是决策层可见的有限信息投影，不得泄露执行层私有事实。快照带 tick 和规则版本，不能在下游被当作已发生事实。

### 9.2 候选机会

候选集合由当前状态、能力、倾向、战术档案和规则共同生成。战术只能声明机会、职责和约束，不能把固定球员、固定坐标或必然动作写成脚本。

### 9.3 效用与约束

硬约束先过滤，软约束和风险再进入效用。能力/倾向的消费点必须可定位；相同输入下只有声明的输入和随机种子可以改变结果。

### 9.4 执行重校验

意图实施时重新读取当前世界并重跑必要的硬约束。世界变化时动作应取消、降级或记录为改变，不能强行执行过期计划。

### 9.5 传球事实统一

传球释放时冻结传球事实、目标语义和飞行参数；接球人只能依据可见状态形成自己的估计。球的运动可达性、接球人的位置和接球技术是不同判据，不能由三个模块各自创造落点。

**出口条件**：成功接球、掉球、点掉、出界和修正落点都有独立事件；评判器直接消费这些事实，不从相邻帧重构因果。

### 9.6 决策 trace 完整性

每个候选机会、约束结果、效用、采样结果、执行重校验和最终动作都可关联到回合与事件。缺失 trace 视为证据缺口。

## 10. 战术与防守档案

### 10.1 合法档案语义

战术档案可以声明槽位、能力需求、机会类型、触发条件、优先级、对位偏好和约束；不能声明某个球员必然执行某动作，也不能直接写物理世界。

### 10.2 档案版本

档案 schema、ID、兼容策略和规则来源必须版本化。增加档案应优先是数据变更；需要 Rust 分支时必须登记为什么 schema 无法表达。

### 10.3 槽位适配

slot fill 是从球员能力/倾向和档案需求派生的纯函数。适配结果必须携带责任和解释，不得用数组顺序、球员编号或隐藏角色替代能力匹配。

### 10.4 防守责任图

防守档案按 `docs/basketball.md` §4 执行对位、延误、挤过、绕过、换防、沉退、协防、补位和回位。每种策略都要有：

1. 触发条件；
2. 责任主体和接替关系；
3. 执行动作及其重校验；
4. 失败或降级事实；
5. 可观测的方向性响应。

只改变展示字符串、目标标签或静态倍率不能关闭本差距。

## 11. 能力、倾向与映射

### 11.1 输入分类

能力表达能否做到，倾向表达如何选择；体格是量纲事实；球队和战术档案表达组织意志。运行态耐力、犯规和位置不写回输入档案。

### 11.2 映射层

归一属性到速度、reach、出手高度、概率或效用的映射必须集中、可单测、可解释。曲线形状、边界和权重进入规则通道；子系统不得散落相同公式。

### 11.3 响应证据

每个保留维度至少有消费点、正向扰动、可观测响应和断路负面对照。不能证明消费链的维度只能留在提案或从运行 schema 移除。

## 12. 运动、接触和防守物理

### 12.1 运动模型

加速、制动、变向、球飞行、控制交接和碰撞必须受能力、规则上限和单位约束。连续运动与离散生命周期布置分开；球位置不能由多个互相竞争的采样来源决定。

### 12.2 空间事实与语义

physics 只发布位置、速度、碰撞和弹道事实；semantics 将事实解释为篮球接触/空间语义；officiating 根据语义和联赛档案裁决。禁止下游反向改写物理事实。

### 12.3 接触与犯规

每类接触有语义分类、吹罚条件、NoCall 路径和罚则程序。边际随机性必须受规则和种子控制，不能用隐藏概率绕开事件流。

## 13. 阵容、疲劳与教练

### 13.1 阵容真相

输入档案、首发标记、运行态在场名单和替补资格分开。数组顺序不是身份；换人事件是事实，不能由快照差分猜测。

### 13.2 疲劳模型

疲劳由负荷、恢复、比赛时钟和档案能力共同决定，运行态数据不回写输入档案。任何负荷输出都必须有单位、范围和责任方。

### 13.3 换人决策

换人由规则强制条件、轮换档案、运行态和教练策略共同决定，并在合法死球窗口执行。拒绝换人或替补不足也应是可解释事实。

## 14. 联赛规则与程序

### 14.1 档案覆盖程序

`LeagueProfile` 按 `docs/basketball.md` §6 表达计时、进攻时钟重置、罚则形式、违例开关、暂停配额、交替拥有、节末和死球程序。

### 14.2 物理与语义分轴

人体和球的物理约束不因联赛复制代码；计时、犯规、几何语义和罚则由 profile 参数化。切换 profile 不得产生同语义的引擎分支。

### 14.3 情景矩阵

每个支持 profile 都需要程序级情景：进攻时钟重置、个人犯满、球队 bonus、罚球序列、三分几何、交替拥有、节末和加时。完整比赛不是情景矩阵的替代品。

## 15. 评判器、参考数据和校准

### 15.1 裁决结果类型

评判结果至少区分 `Pass`、`Defect`、`NotApplicable` 和 `InsufficientEvidence`。不适用不进入分母；证据不足不贡献真实性；Hard defect 能阻断整体门。

### 15.2 固定分母

每条准则报告机会数、通过数、缺陷数、不适用数、证据不足数和覆盖率。分母由准则定义，不能因结果不理想而改变。

### 15.3 综合指数的限制

指数只能聚合已产生的裁决，用于趋势和归因排序。它不能抵消 Hard gate、账本失败、证据不足或机制负面对照失败。

### 15.4 严格解析

输入流默认严格解析。坏行、缺失关键字段、版本不兼容和顺序破坏必须使评判失败；宽松解析必须是明确的非验收模式。

### 15.5 参考分布数据规格

fixture 是独立、版本化、带来源和口径的数据档案，不能由当前模拟输出反向生成。fixture 要区分联赛、样本范围、统计定义、联合关系和证据局限。

### 15.6 PBP 转换

外部 play-by-play 先经过版本化规范化，保留原始事件、映射、缺失性和不确定性。转换失败不能静默删除事件。

### 15.7 校准协议

校准包必须固定输入、规则/档案版本、种子范围、流模式、输出 manifest 和比较口径，并同时提供机制、分布和反事实证据。默认值变更、fixture 变更和阈值变更必须可区分。

## 16. 协议、CLI 和资源

### 16.1 输入输出

每次运行都带输入 manifest、规则/档案版本、代码或 schema 摘要、随机种子和输出摘要。事实流、帧流、评判流和资源报告不得混为一个未声明格式。

### 16.2 CLI 边界

CLI 只编排生命周期命令和工件输出，不复制引擎真相或评判阈值。失败必须通过结构化结果和退出状态传播。

### 16.3 回放与调试

回放按照 event ID、parent ID、tick 和回合定位；调试视图是事件和快照的投影，不允许 UI 写回比赛状态，**也不允许 UI 重算引擎语义**（不变量判定与投篮因果配对必须消费引擎工件）。

运行/会话分离：单场执行产物（run）与交互式逐 tick 调试（session）是两种时间语义，不得共用一次性大响应端点；事件增量游标必须使用跨 tick 唯一的 `event_id`。

### 16.4 资源治理

流模式、输出范围、临时文件、磁盘预算、内存预算和构建产物必须有明确 owner。默认输出应有界；异常退出也必须清理临时产物并保留失败原因。

完整帧存储使用 gzip 编码（`StreamMode::FramesGzip`），消费者按文件头自动识别；交互式定位优先采用「事实流 + 周期关键帧重放」，不引入自定义分块格式。

## 17. 确定性与守卫

### 17.1 RNG 分流

随机源按职责分流并带稳定命名；增加一类随机性不能无意重排不相关的事件序列。固定输入和种子必须得到可比较的事件摘要。

### 17.2 Replay digest

replay digest 只覆盖声明为事实的字段，并带 schema/规则版本。字段变化要能区分有意行为变化与序列漂移。

### 17.3 常数守卫

影响行为的数字、阈值和档案选择必须经过规则/数据通道。守卫要感知注释和字符串、按文件或符号记录预算，并用负面对照证明确实能拦截新增常数；测试数据和展示换算必须有明确类别。

### 17.4 能力链守卫

属性扰动测试验证消费链，断路测试验证测试本身不会恒绿。守卫不以 roster 顺序、球员编号或单一黄金哈希作为行为证据。

### 17.5 完整性守卫

文档引用、阈值来源、World 公共边界、身份去索引、资源清理和 schema 版本都应有独立守卫。守卫输出必须说明范围，不能把局部通过写成全局通过。

## 18. 测试体系与验收门

### 18.1 单元和模型测试

状态转换、账本平衡、解析、映射和 profile 规则都要有正向与负向测试。模型测试覆盖非法边和边界值。

### 18.2 属性与机制测试

对能力、倾向、战术档案、防守方案和规则 profile 做单变量扰动，并检查方向性和因果 trace。负面对照必须能使测试失败。

### 18.3 情景测试

每个生命周期边、联赛程序、球态边、传球层次和防守责任都应有最小可复现场景。情景工件必须带输入 manifest。

### 18.4 批量测试

Smoke、Regression 和 Calibration 使用不同目的、样本量和通过标准；不能以一次短跑代替完整矩阵，也不能把矩阵结果压成单一指数。

### 18.5 性能测试

性能报告区分纯引擎、事实输出、评判和批量模式，固定硬件/预算上下文，并保留输出规模和资源使用证据。性能优化若改变事实语义，必须按行为变更验收。

### 18.6 必须通过的硬门

关闭一个跨周期差距至少需要证明：

1. L1 Hard 违反在声明范围内为零；
2. 事件、回合和账本可独立重建并对平；
3. Hard gate、证据不足和解析失败会阻断或明确失败；
4. 能力/战术/规则扰动有可解释响应，断路负面对照有效；
5. 固定输入可重放，输出带完整 manifest；
6. profile 情景和资源预算通过；
7. 当前状态已更新，原始证据和周期记录已归档到正确工作面。

### G6a · 禁区出手分布（开放，2026-09-20 实测，含负结果）

出手距离分布严重失真：实测篮下（≤4 ft）仅 1–2%、三分 69–74%
（真实 NBA：篮下 ~30%、三分 ~40–45%）。四次校准迭代的实测：

| 迭代 | 参数 | 三分占比 | 3P% 中位 |
| --- | --- | --- | --- |
| v66 基线 | — | 74% | 35.8（带内） |
| 1 | 距离参考 47→30 + 效用斜率/openness 激进值 | 67–72% | 19.6–23.5（跳带） |
| 2 | openness 0.45/slope 0.8 | ~70% | 29.8（跳带） |
| 3 | openness 0.50/slope 0.75 | ~73% | 25.9（跳带） |
| 4 | 突破链（bias 2.0–3.0、finish 10–14） | ~73% | 28.1–29.9（跳带） |

**结论**：命中率对效用形状与攻框比例高度敏感、方向非单调；分布失真
的根因是攻框行为链缺失，效用参数无法闭合分布问题，且强行抬高攻框
会砸穿 3P% 门（攻框比例与 3P% 强耦合，需要命中率模型联合校准）。

剩余根因（行为链缺失，关闭需一个小周期）：

1. 无球切入接球后直接跳投，没有「切入攻框」候选；
2. 抢到前场篮板后没有直接二次攻框路径；
3. 快攻（transition）没有形成篮下终结的候选生成；
4. 五外站位把全部无球人固定在外线，没有篮下落位。

突破链参数已回滚至 v66 原值（rim_attack_bias 1.2、finish_range 16）；
禁止用效用参数硬凑分布数字，也禁止单独抬攻框比例。

**实施状态（2026-09-24）**：四条行为链已全部落地，效用通道与规则字段均经
`check_inline_constants` 守卫（charter C1）：

1. 前场篮板二次攻框：`ConstraintContext.possession_had_shot` + Shoot 效用
   `effective_putback_bias × rebound.putback_distance_discount`
   （`rebound_putback_distance_discount` 6-seed 扰动可见性恢复）；
2. 转换期篮下终结：`possession_elapsed_seconds` + `transition_finish_window_seconds`
   (6s) × `transition_finish_bonus` (0.35)，窗口外零影响；
3. 弱侧背切：`SlotBehaviour::BackdoorCut`（`backdoor_cut_depth_ratio` 0.85），
   five_out 右翼槽位启用；
4. 下沉禁区：`SlotBehaviour::DipToRim`（`dip_to_rim_depth_ratio` 0.7），
   five_out 右底角槽位启用；传球侧配套 `decision.rim_catch_bonus`（接球人
   处于篮下时传球效用按 finishing 叠加）。

分布级验收（rim_share 回到 [0.25, 0.5] 带）仍开放：效用通道已通，
实测 rim(4ft) 出手占比 1.7%→7.1%（突破终结起跳延伸
`drive_finish_extend_ft` = 6.0 后）；剩余缺口需要突破终结总量与三路
rim 出手来源（转换/二次进攻/无球切入接球）联合收敛，单杠杆实验
（`drive_rim_attack_bias` 2.2 负反馈回退、延伸量 3→6 饱和）已证明
非单调耦合，归入全周行为校准。
附带修复：封盖后球出界的回合终端语义（封盖松球显式
`TurnoverLooseBall` + 评判器 `BLOCKED_SHOT` 原因事实），seed 43 的
`TURNOVER_ATTRIBUTION` Hard 1→0；松球争抢被残留持球动作锁死
（seed13 poss#64 卡死 616s，`POSSESSION_DURATION_BOUNDS` Hard 来源，
动作锁定增加球在手的语义前提），17-seed 矩阵复测 0 Hard。

## 21. 最终判断标准

### 21.1 它不会说谎

系统不发布与世界矛盾的事实；不能解释的结果成为显式失败或证据不足。

### 21.2 它会打篮球，而不是播放战术动画

球员能力、倾向、教练、战术和防守在约束下产生机会和选择；防守能打断计划，动作能降级，结果能改变后续状态，且变化能沿事件和 trace 解释。

### 21.3 它能被验证和改进

研究者可以从缺陷定位到回合、事件、责任子系统和输入通道，并通过固定输入重放比较改动。

### 21.4 它能被别人使用

配置、运行、比较、回放和导出不需要修改引擎源码；失败有结构化原因，资源边界可预见，文档入口不会把历史记录冒充当前状态。
