# NBA-Sim · 校准与验收协议

> 定位：项目的过程规格。本文档规定如何修改影响行为的参数、如何组织证据、如何判定阶段出口。
> 上游文档：`docs/charter.md`、`docs/architecture.md`、`docs/quality.md`、`docs/attributes.md`、`docs/tactics.md`。
> 关联工作面：`docs/dev/roadmap.md`、`docs/dev/status.md`、`docs/dev/current/plan.md`。
> 修订纪律：只写可长期复用的流程和验收语义；当前实现、命令、实测结果和历史决策进入 `docs/dev/` 或 `docs/decisions.md`。

## 0. 文档目的

本文档回答三个问题：

1. 如何校准：影响行为的参数必须通过什么通道改变；
2. 如何验收：一个里程碑或结构改动需要哪些证据；
3. 如何闭环：如何从评判缺陷回到受控改动，再回到可复现验证。

验收对象分成三类：

- **结构门**：模块边界、单一事实源、状态边和数据 schema；
- **机制门**：能力/规则/状态是否真正影响机会、执行和裁决；
- **观测门**：事件、账本、逐回合评判和参考分布是否完整。

任何综合指数都不能抵消结构门或机制门失败。

## 1. 校准协议

任何改变行为的默认值、公式系数、参考 fixture 或规则档案，都必须形成一个可复现的校准包：

1. **声明对象**：说明改动属于规则、能力、倾向、战术、联赛档案还是评判参考数据；
2. **保留基线**：固定输入、随机种子范围、scope、输出模式和 fixture 版本；
3. **走正确通道**：实验参数使用规则/档案覆盖，确认后才改变默认配置；
4. **提供三层证据**：机制响应、参考分布变化和适用的反事实场景；
5. **记录缺陷变化**：报告逐条缺陷、证据覆盖、Hard gate 和 top attribution 的前后差异；
6. **处理确定性**：行为有意变化时更新 replay/golden 记录，并说明变化属于哪一条规格；
7. **保持单一职责**：校准、结构重构、性能优化和展示变更不得混成无法归因的一次改动。

禁止以下替代方案：

- 改默认值后只跑一场并目测；
- 用扩大参考带、改变分母或把证据不足改成 Pass 制造绿色；
- 把新行为系数留在子系统源码中；
- 用黄金哈希不变证明真实性，或用统计进带证明机制正确。

## 2. 验收标准

### 2.1 里程碑门

里程碑的名称和依赖由 `docs/dev/roadmap.md` 定义；本节定义每类门的出口条件。

**M1 · 不变量内建**

- 每个发布 tick 都执行 L1 规则；
- 每条违反带规则 ID、tick、严重度和可读详情；
- 违反进入结构化工件，Hard 违反能阻断调用方；
- 合成负面对照能捕获双持球、球人分离、比分/时钟倒退等错误。

**M2 · 球态收敛**

- 球权/最后触球事实只有一个权威来源；
- 状态边由领域转换函数和穷举测试定义；
- holder、has-ball、team possession 和运动位置均为派生视图或不可变状态载荷；
- 非法边不能由普通调用路径构造。

**M3 · 确定性基线**

- 相同输入包和种子得到相同事件序列与状态摘要；
- replay/golden 工件进入持续回归；
- 批量输出包含输入 manifest、规则/fixture 版本和结果摘要。

**M4 · 阶段管线**

- 阶段顺序显式；
- 每个阶段有独立的输入/写权限和测试；
- 不变量阶段不可被短路路径绕过；
- 结构重构若声明行为中性，必须证明事件语义和确定性基线保持。

**M5 · 执行重校验**

- 意图实施前重新检查当前世界的硬约束；
- 世界变化时动作降级、取消或记录为改变，不强行执行旧意图；
- trace 能统计重校验结果。

**M8 · 回合/阶段评判**

- 每个回合和阶段转换有裁决或显式证据不足；
- 评判使用版本化参考分布；
- `judgments`、归因账本和不变量工件可相互定位；
- Hard 缺陷使总体门失败，不能被综合指数抵消。

**M7 · 参数收编**

- 行为参数进入规则/档案通道；
- 评判和审计工具不复制运行时阈值；
- 常数守卫、阈值完整性守卫和负面对照有效。

**M9 · 能力涌现**

- 每个保留能力/倾向维度至少有一个消费点和一个可观测响应；
- 正向扰动和断路负面对照都进入回归；
- 响应不能依赖 roster 顺序、球员 ID 或隐藏脚本。

**M10 · 多联赛**

- `LeagueProfile` 表达计时、犯规、bonus、几何和程序语义；
- semantics/officiating 接收事实与 profile，而不是联赛专用分支；
- 每个支持的 profile 有程序级情景矩阵和完整事件工件。

### 2.2 持续质量门

| 门 | 通过条件 |
| --- | --- |
| L1 | 全部 Hard 物理/状态不变量为零 |
| 因果 | 每个得分、失误、篮板、罚球和回合终结都有可追溯来源 |
| 覆盖 | 回合/阶段裁决无静默遗漏；证据不足单独计数 |
| 机制 | 能力、战术和规则扰动在声明的观测量上有响应 |
| 确定性 | 同输入 replay digest 稳定 |
| 资源 | 输出、内存、临时文件和构建产物不超过已批准预算 |
| 校准 | top 缺陷的变化能由单一改动解释，并附反事实或机制证据 |

sanity net 的具体带宽属于带版本的评判 fixture 或周期门，不在本协议中复制当前实测值。

### 2.3 架构门

- 依赖方向符合 `architecture.md`，领域层不依赖上层业务；
- 事实事件、状态快照、评判器和 UI 不形成第二个可写真相源；
- 新增不变量只需扩展检测层，不要求业务层复制判定；
- 新增战术或联赛档案不要求添加同语义的引擎分支；
- 规则参数、参考 fixture 和守卫基准有清晰的 owner 与版本。

### 2.4 工具链门

工具链必须能完成以下能力，但具体命令由实现和 CI 提供：

- 读取严格的事件/事实流，解析失败不可静默丢弃；
- 输出不变量、评判、归因和账本工件；
- 支持规则/档案覆盖与固定输入重放；
- 在 Hard gate 失败时向调用方传播失败；
- 记录 manifest、版本、摘要和资源报告；
- 运行文档、常数、阈值、公共边界和资源守卫及其负面对照。

## 3. 校准闭环

```text
生成 → 检查不变量 → 逐回合/逐阶段评判
     → 归因 → 选择一个责任通道
     → 规则/档案/能力改动 → 机制与反事实验证
     → 确定性复验 → 保存证据包
```

闭环规则：

1. 选题来自归因账本和证据盲区，不来自单场目测；
2. 结构因果门优先于统计带；
3. 参考分布只提供回归信号，不能替代机制守卫；
4. 参数改动必须能从输入 manifest 重放；
5. 如果证据不足，结果是“未判定”，不是“通过”。

## 5. 术语表

| 术语 | 定义 |
| --- | --- |
| **校准包** | 固定输入、规则/档案版本、输出工件、比较结果和解释的可复现实验包 |
| **结构门** | 对事实源、模块边界、状态边和数据 schema 的验收 |
| **机制门** | 对输入扰动、机会生成、执行和裁决响应的验收 |
| **观测门** | 对事件、账本、评判覆盖和参考分布工件的验收 |
| **Hard gate** | 任何失败都不能被综合指数抵消的阻断门 |
| **sanity net** | 只能捕获明显荒谬聚合结果的粗筛，不是真实性证明 |
